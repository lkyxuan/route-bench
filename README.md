# route-bench：宝路由测试基准

用户对助理说一句话，路由要决定这句话交给谁：哪个宝、宝下面哪段讨论串，还是直接答、新建一个宝、拆成几件分别交。这个仓库用 100 个宝和 1000 句话来测一个路由分得准不准、快不快、费多少 token。任何路由方案都能接进来测，不限于 Kiki。

## 题库

| 类别 | 句数 | 测什么 |
| --- | --- | --- |
| 单句新开 | 500 | 每个宝 5 句，有直白的，也有要推理的（“App 打开就闪退”→ 开发宝） |
| 接已有讨论串 | 140 | 70 段讨论串各 2 句，要认出是哪段讨论串的后续 |
| 连续对话 | 192（51 段） | 在奇奇里连着说的几句，有指代（“那就 Air 吧”）、有中途插别的事、有“回到刚才” |
| 一句多件事 | 60 | 要拆开分别交（“记一笔打车 45，另外看下 BTC”） |
| 该新建宝 | 50 | 现有 100 个宝都不管的事（攀岩、考驾照、留学） |
| 该直接答 | 58 | 打招呼、问时间、常识，奇奇自己答，不进任何宝 |

100 个宝分 11 组（工作、开发、投资、生活、健康、学习、家庭、创作、兴趣、系统、杂项），故意放了容易混的：记账宝和家庭账宝、英语宝和日语宝、健身宝和跑步宝、加密宝和链上宝和量化宝。

文件：

- `data/baos.json`：宝列表，每个宝有名字、分组、负责什么、讨论串（名字 + 一句摘要）。
- `data/singles-*.txt`、`threads.txt`、`episodes.txt`、`special.txt`：手写的题目，格式写在每个文件开头。
- `data/cases.jsonl`：编译好的题目，测试程序只读它。改了 txt 要跑 `npm run build`。

## 怎么跑

不用装依赖，Node 20 以上就行：

```bash
node bench.mjs --router keyword                    # 关键词基线
node bench.mjs --router "exec:python3 adapters/vector.py"   # 向量基线（要先装 onnxruntime，见文件开头）
node bench.mjs --router http://127.0.0.1:8080/route        # 你自己的路由服务
```

选项：`--limit 100` 只跑前 100 组，`--only single,episode` 只跑这几类，`--concurrency 4` 同时跑几组（连续对话组内按顺序），`--out reports` 报告放哪。

跑完在 `reports/` 下出两个文件：`.md` 是报告（总分、分类得分、耗时、token、错题表），`.jsonl` 是每句的原始结果。

### 测 Kiki 现在的路由

在装好依赖的 kiki-pro 目录里跑（要用到它的 `src/route.ts` 和 tsx）：

```bash
cd ~/kiki-pro
ROUTE_API_KEY=sk-你的DeepSeek密钥 node ~/route-bench/bench.mjs --router "exec:npx tsx ~/route-bench/adapters/kiki.mts"
```

默认用 DeepSeek 的 `deepseek-chat`，换模型设 `ROUTE_API_BASE`、`ROUTE_MODEL`（任何 OpenAI 兼容接口都行）。分派规则默认读 `~/kiki-data/分派规则.md`。100 个宝时每句提示词大约 5000 token，跑完 1000 句约 500 万 token 输入。

## 怎么接你的路由

路由收到的请求（每句话一次）：

```json
{
  "id": 17,
  "text": "那就 Air 吧",
  "history": [{ "text": "帮我看看 iPad 现在哪个版本值得买", "routedTo": { "type": "route", "bao": "购物宝", "thread": "买iPad" } }],
  "current": { "bao": "购物宝", "thread": "买iPad" },
  "baos": [{ "name": "购物宝", "group": "生活", "desc": "买东西、比价、选型、退换货", "threads": [{ "name": "买iPad", "summary": "比较 iPad Air 和 Pro，倾向 Air" }] }]
}
```

- `history`：同一段连续对话里前几句和它们的**正确**去处（前面分错了不会连累后面）。
- `current`：用户眼下所在，等于上一句的正确去处；第一句是 `null`。
- `id`：只有 exec 接法有，回答要原样带回。

路由要回的（下面几种之一）：

```json
{ "type": "route", "bao": "购物宝", "thread": "买iPad" }
{ "type": "route", "bao": "购物宝", "thread": null }
{ "type": "new", "about": "攀岩、抱石" }
{ "type": "reply" }
{ "type": "split", "targets": [{ "bao": "记账宝", "thread": null }, { "bao": "加密宝", "thread": null }] }
```

`thread` 为 `null` 或 `"主对话"` 表示交给宝的主对话。可以多带两个字段让报告更有用：`usage: { "input": 1234, "output": 30 }` 统计 token；`layer: "规则"` 统计是哪一层拍的板（分层路由用）。

三种接法：

1. **exec**：`--router "exec:你的命令"`。测试程序起一个子进程一直开着，往 stdin 一行写一个请求，从 stdout 一行读一个回答（带同一个 `id`）。可以乱序回答，调试信息写 stderr。`adapters/vector.py` 是 Python 写的例子。
2. **http**：`--router http://…`。每句 POST 一次请求 JSON，回答 JSON。
3. **内置**：`adapters/keyword.mjs` 那样写一个函数，在 `bench.mjs` 里登记。

## 怎么算分

- **去对宝**（主指标）：回答类型对，宝也对。拆分要拆出的宝和答案完全一样（多拆少拆都算错）。
- **连讨论串也对**：去对宝的基础上，讨论串也对；答案是主对话时，回答也得是主对话。
- 报告里连续对话再分三类：第一句、接着上一句（去处没变）、换了去处。“接着上一句”测上下文粘性，“换了去处”测会不会被粘住。
- 出错、超时、回答格式不对都算错。

## 基线成绩（2026-11-08）

| 路由 | 去对宝 | 单句新开 | 接讨论串 | 连续·接着 | 连续·换去处 | 拆分 | 新建 | 直接答 | 每句耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 关键词（`keyword`） | 46.2% | 34.6% | 86.4% | 82.1% | 42.9% | 0% | 0% | 50.0% | <1ms |
| 向量（bge-small-zh） | 50.0% | 58.4% | 90.0% | 23.6% | 48.6% | 0% | 0% | 0% | 2ms |
| Kiki 现在的路由 | 待在 Mac 上跑 | | | | | | | | |

两个基线都不会新建、拆分，所以那两类是 0。“接讨论串”偏高，因为题目和讨论串摘要用词重合多，真实用户说得更含糊，这一类以后要补难题。

## 题目的已知局限

- 全是手写的模拟数据，不是真实对话。以后可以从真实日志里脱敏抽一批补进来。
- 少数单句可能同时说得通两个宝（比如“Workers 冷启动慢”可以是后端宝，也可能是邀请码服务那段讨论串），看错题时人工复核。
- “该新建宝”尽量挑了现有宝都不管的领域，但“跳槽求职”和招聘宝、“恋爱情感”和心理宝还是有点擦边，是故意留的难题。
